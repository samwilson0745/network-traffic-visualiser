# Docker Network Traffic Visualizer

A local, self-contained network observability system: three Dockerized
systems generate real Internet traffic, a Go collector captures and
aggregates it into flows, and a React/D3 graph shows it updating live.

Scope: only traffic generated by the three Dockerized systems inside this
project's own Docker network is observed. The host machine, Wi-Fi, router,
and other devices are never touched.

## Architecture

```
system-1/2/3 (traffic generators)
        │
   traffic-net (Docker bridge, 172.31.0.0/24)
        │
   collector (gopacket/libpcap, host network mode)
        │  packet metadata over websocket
        ▼
   backend (Go) — flow aggregation + /ws broadcast
        │
        ▼
   frontend (React + D3) — live graph, stats, per-flow detail
```

- **system-1**: repeated HTTP/HTTPS GETs.
- **system-2**: periodic API calls to a couple of endpoints.
- **system-3**: mixed DNS lookups + HTTP/HTTPS requests.
- **collector**: captures packets on the Linux "any" pseudo-device
  (requires `network_mode: host` + `NET_RAW`/`NET_ADMIN`), filters to the
  `traffic-net` subnet, and streams packet metadata to the backend.
- **backend**: aggregates packets into flows keyed by
  (system, destination IP, protocol), and broadcasts a snapshot every
  second over `/ws`. No database — everything is in memory (per the V1
  scope in the spec).
- **frontend**: force-directed graph (systems in blue, destinations in
  orange), a stats panel, and a click-to-inspect flow detail panel.

## Running

```bash
docker compose up --build
```

Then open http://localhost:3000. Traffic should appear within a few
seconds as the three systems start making requests.

- Frontend: http://localhost:3000
- Backend WebSocket (frontend feed): ws://localhost:8080/ws
- Backend health check: http://localhost:8080/healthz

## Configuration

Traffic destinations/intervals are configurable via environment variables
in `docker-compose.yml` (`TARGETS`, `HOSTS`, `INTERVAL_SECONDS`). The
aggregation window and flow idle timeout are configurable on the backend
(`AGGREGATION_WINDOW_MS`, `FLOW_IDLE_TIMEOUT_SECONDS`).

## Notes / limitations (V1)

- No database — flow state lives in the backend's memory and is lost on
  restart.
- No DNS-to-hostname correlation yet — destinations are shown as IPs.
- No authentication, no Kubernetes, no Kafka, no cloud deployment — all
  out of scope for V1, per the design doc.
- `collector` uses `network_mode: host`, which on Docker Desktop runs
  inside the Docker VM's network namespace — this is what lets it see the
  Docker bridge traffic between the other containers and the internet.
